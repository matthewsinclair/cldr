## What is wrong

hv has ruled that devbin's dev/opt/brew contract (devbin's `docs/dev-opt-brew.md`) is the one approach for a Rust CLI on macOS released through Homebrew: every project uses it, with every difference removed. Cldr does not follow it yet, in three places.

- **No publish and no switch.** `src/cli.rs:84-101` dispatches `help`, `--version`, `paths`, `doctor`, `export`, `data`, `check`, `render`, `briefing` and `month`. There is no `cldr install` to publish an opt tree (T2) and no `cldr use [dev|opt|brew]` (T5; devbin's own is its `lib/cmd/use`). So a maintainer cannot switch between a dev, an opt and a brew cldr: whichever cldr is first on PATH answers, and nothing reports or checks which. `cldr doctor` (`src/doctor.rs`) has no shadow check (T5): it never looks at PATH or at the running binary.
- **No tree identity, and a bare version line.** `src/cli.rs:89-90` prints `cldr <version>`, not T4's `cldr <version> (<tree>, <sha12>[+dirty])`, and nothing in cldr names the tree it runs from.
- **The formula is out of step.** `packaging/homebrew/cldr.rb:31-37` lays out the keg itself (`libexec.install "bin"`, `pkgshare.install "config.toml"`) and ends with devbin's `@@FINISH@@`, where Pplr's and Ccusage's macOS formulas use `@@INSTALL@@`, the install body devbin generates. The keg gets a T3 manifest that cldr never reads: nothing under `src/` or `tests/` mentions one.

## How to see it

From the code at 9cfc0d7, which vendors devbin 0.1.20 in `bin/devbin` and `bin/.devbin/lib/`: `cldr use dev` falls to the unknown-command arm (`src/cli.rs:101`), and `cldr --version` prints the version alone. Cldr has never had any of this, so it is a gap against the ruling, not a regression.

## Severity

Medium: a consistency and maintenance defect, with no data or security risk.

## Fix outline

devbin-vc's recommendation, not yet ruled on by hv:

- Adopt the one implementation hv chooses for every tool. devbin-vc recommends that devbin's core carry it for a project's own binaries, and has proposed a devbin issue to hv; Cldr would then declare its link name and opt prefix in its config.
- The formula likely moves to `@@INSTALL@@`, with `config.toml` as a packed file.

From the contract, for whoever picks this up:

- T4 reads a compiled tool's sha from its binary, never from HEAD at run time, and marks it `+dirty` when the binary was built from dirty build inputs, derived from the build system's own record (eg cargo's dep-info). So cldr's build has to stamp both into the binary.
- devbin 0.1.20 accepts `@@FINISH@@` for a template whose assets need laying out (`bin/.devbin/lib/cmd/formula:448-451`), and T2 counts a formula that lays out signed release assets and writes T3's manifest as conforming. The formula is valid today; what changes it is the ruling's "every difference removed", against Pplr's and Ccusage's `@@INSTALL@@`.

## Done when

`cldr install`, `cldr use [dev|opt|brew]`, the version line and doctor's shadow check behave exactly as devbin's do. The contract's own proof for a tool is T10: `use dev`, `use opt` and `use brew` in turn, each followed by the version line and doctor, with the shadow check passing.
